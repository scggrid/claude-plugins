화면이 안 보인다는 신고를 받으면, 방금 바꾼 코드를 먼저 열지 않는다. 이 문제에서 가장 흔한 실수가 그것이다. 실행되는 환경이 여러 개(로컬 개발서버, 프리뷰, 운영)이고, 코드 버그처럼 들리는 신고가 실제로는 환경 차이(주소가 다름, 배포 보호 화면, 배포가 아직 안 됨, 서버 환경에서만 걸리는 한도)인 경우가 자주 있다. 계층을 잘못 잡으면 멀쩡한 코드를 고치게 된다.

## 1. 무엇을 보고 시작하는가

세 가지가 있어야 시작할 수 있다.

- **정확한 주소** — 화면에 떠 있는 주소를 그대로. "로컬"이라는 말만으로는 부족하다.
- **정확한 증상** — 안 열림 / 계속 로딩 / 하얀 화면 / 에러 메시지(그대로) / 로그인만 안 됨.
- **언제부터, 매번인지** — "아침부터 매번"과 "가끔"은 원인 계층이 다르다.

신고에 이미 있는 것은 다시 묻지 않는다. 빠진 것만, 그중에서도 다음 한 걸음을 정하는 데 실제로 필요한 것만 묻는다. 세 개를 채우는 것이 목적이 아니다. "운영에 반영이 안 됐다"는 신고에서 정확한 주소는 거의 의미가 없고 어떤 커밋인지가 필요하다. 질문은 세 개를 넘기지 않는다.

물어보는 답은 짧아야 한다. 아직 아무것도 확인되지 않은 상태에서 "A라면 이렇고 아니면 저렇다"는 분기를 미리 펼치지 않는다. 읽는 사람이 답하기도 전에 읽을 것이 많아지면 답이 늦게 오고, 그러면 진단도 늦어진다. 가설은 답을 받은 뒤에 펼친다.

짧게 만드는 대상은 그 분기뿐이다. 다음 두 가지는 짧게 만들려고 빼면 안 된다.

- **확인 비용이 싼 한 줄 질문.** 무료 플랜인지 같은 것은 답 한 줄로 원인이 갈리므로, 물어보는 김에 같이 묻는다. 나중에 물으면 그만큼 늦어진다.
- **지금 시점의 짐작.** "뭐가 문제야"라고 물은 사람에게 질문만 돌려주지 않는다. 유력한 후보를 한 줄씩, 두세 개까지 적고 무엇으로 갈리는지 붙인다. 확정이 아니라고만 분명히 하면 된다.

사용자를 존댓말로 대한다.

환경 후보는 넷이고, 헷갈리는 것이 셋째와 넷째다.

- **사용자 PC의 개발서버** — 사용자가 직접 띄운 것.
- **PR 프리뷰** — 브랜치별로 따로 올라간 배포. 환경 변수와 DB 경로가 운영과 다르다.
- **운영** — `main`에 들어가고 배포까지 끝난 것만 보인다. 이 저장소는 `main`에 바로 푸시하므로, 아직 푸시가 안 됐거나 배포가 도는 중이면 안 보이는 게 정상이다.
- **내가 띄운 개발서버** — 브라우저 도구로 화면을 보고 있다면 그건 내 실행 환경이고 사용자 PC가 아니다. 여기서 잘 되는 것은 사용자 PC에서 된다는 뜻이 아니다.

## 2. 지루한 원인부터 확인한다

실제로 원인이었던 빈도 순서다. 위에서부터 내려간다.

1. **주소와 접근 권한.** 프리뷰 주소가 앱이 아니라 배포 플랫폼 로그인 화면으로 튀는 경우가 있다. 화면의 제목과 글자를 읽어서 확인한다. 이건 앱 로그인과 아무 상관이 없고 고칠 코드도 없다.
2. **운영에 반영이 안 됐다.** 그 변경이 `origin/main`에 실제로 있는지(`git log origin/main -5`), 그리고 배포가 그 커밋으로 끝났는지 확인한다. 둘 중 하나라도 아니면 안 보이는 게 맞다.
3. **요청이 서버까지 갔는지.** 개발서버 로그나 네트워크 기록에서 실패한 경로의 요청이 보이는지 본다. 클릭했는데 아무 요청도 안 남으면 문제는 브라우저 쪽(스크립트 에러, 화면 전환이 멈춤, 캐시)이고, 서버나 DB를 고쳐도 그대로다. 사용자의 브라우저를 볼 수 없으면 콘솔과 네트워크 탭을 보여달라고 한다.
4. **가끔만 된다.** 같은 조작이 어떤 때는 되고 어떤 때는 안 되면 로직보다 한도(DB 동시 연결 수, 함수 실행 시간) 쪽이다. 다음 단계로 간다.

## 3. 재현으로 확인한다

"가끔 안 된다"는 추측으로 결론 내지 않는다. 같은 요청을 연달아 5~10번 실행해서, 한 번 실패하고 여러 번 빨리 성공하는 식의 기록을 남긴다. 그 기록이 근거가 된다. "아마 연결 수 문제인 것 같다"보다 훨씬 쓸모 있고, 고친 뒤 사라졌는지 같은 방법으로 다시 확인할 수 있다.

확인용으로 만든 임시 스크립트는 확인이 끝나면 지운다.

## 4. 원인 계층에 맞게 고친다

- **주소·배포·환경 차이** — 코드를 고치지 않는다. 왜 환경이 다른지 설명하고 끝낸다. 여기서 코드를 손대면 멀쩡한 것을 망친다.
- **설정** — 고친다. 무엇을 어떤 값으로 바꿨는지와 되돌리는 방법을 한 줄로 남긴다.
- **코드** — 고친다.

무한 로딩을 무한 로딩으로 남기지 않는다. 근본 원인을 아직 다 못 잡았어도, 실패가 몇 초 안에 읽을 수 있는 에러로 끝나게 만드는 것이 끝나지 않는 화면보다 항상 낫다.

고친 뒤에는 2~3단계에서 쓴 것과 같은 방법으로 다시 확인해서 증상이 사라졌는지 본다.

## 5. 보고 순서

1. **원인 계층 한 줄** — 코드 / 설정 / 배포가 안 됨 / 접근 권한 화면 / 브라우저 쪽 중 무엇이었는지. 사용자가 원인을 직접 지목했다면("코드가 덮어써진 거야?") 그것이 맞는지부터 첫 줄에 답한다.
2. **근거** — 무엇을 보고 그렇게 판단했는지. 재현 기록, 로그 한 줄, `git log` 결과.
3. **고친 것** — 무엇을 어떻게. 고칠 게 없었다면 왜 없었는지.
4. **확인할 것** — 사람이 직접 볼 화면이나 동작 하나.
5. 원인이 여러 개면 다 적는다. 느린 요청과 배포 누락과 연결 수 한도가 한꺼번에 겹치는 일이 실제로 있다. 하나로 압축하면 나머지가 다음 주에 다시 올라온다.

확인된 것과 아직 추정인 것을 섞어 쓰지 않는다. 확인된 것만 근거로 올리고, 추정은 추정이라고 쓴다.

## 하지 말 것

- 환경이 여러 개 섞인 신고에서 코드부터 열지 않는다. 주소를 눌러보거나 `git log`를 보는 건 몇 초면 끝난다.
- 확인 질문을 길게 늘리지 않는다. 신고에 이미 있는 것을 되묻거나, 답을 받기 전에 가능한 경우를 다 나열하지 않는다.
- 재현 없이 원인을 단정하지 않는다.
- 원인을 하나로 압축하지 않는다.
- 계정 이름, 비밀 키, 개인 PC 경로를 보고서에 옮겨 적지 않는다.
- 잘했다/나쁘다 평가는 하지 않는다. 어느 계층이 원인이었는지만 말한다.
