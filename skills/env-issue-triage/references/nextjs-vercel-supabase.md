# Next.js + Vercel + Supabase + Drizzle 상세

SKILL.md의 2단계(지루한 원인부터)에 들어갈 때 읽는다. 이 조합에서 실제로 원인이었던 것들이고, 위에서부터 확인 비용이 싼 순서다.

## 1. 배포 보호 화면 (Vercel Deployment Protection)

프리뷰 주소를 열었는데 앱이 아니라 로그인 화면이 나오면, 팀 접근 권한 게이트일 가능성이 높다. 화면 제목이 `Login – Vercel`이면 그것이다.

- 앱의 로그인 기능과 무관하다. 앱 코드에 문제가 없다.
- 고칠 코드가 없다. 사용자가 해당 팀 계정으로 로그인해야 하거나, 프로젝트 설정에서 프리뷰 보호를 풀어야 한다. 설정 변경은 사용자에게 맡긴다.
- "로그인이 안 된다"는 신고의 상당수가 여기다. 앱 인증 코드를 읽기 전에 화면 글자를 먼저 확인한다.

## 2. 배포가 아직 안 됐다

이 저장소는 `main`에 바로 푸시한다. 운영에 안 보인다는 신고는 다음 순서로 확인한다.

```bash
git log origin/main -5 --oneline   # 그 변경이 origin/main에 있나
git status                          # 로컬에만 있고 푸시가 안 된 건 아닌가
```

`origin/main`에 커밋이 있어도 배포가 도는 중이거나 빌드가 실패했으면 이전 버전이 그대로 떠 있다. Vercel 대시보드에서 마지막 성공한 배포가 어느 커밋인지 확인한다. 빌드 실패면 그 로그가 원인이고, 앱 동작을 아무리 봐도 안 나온다.

## 3. 요청이 서버까지 갔는지

- 개발서버를 도구로 띄워 놓았다면 `preview_logs`로 로그를 본다.
- 실패한 경로(`/dashboard` 등)의 요청 줄이 아예 없으면 서버는 요청을 받지 못했다. 원인은 브라우저 쪽이다: 스크립트 에러, 화면 전환(router)이 멈춤, 캐시된 예전 번들.
- 이 경우 느린 쿼리를 고치거나 연결 수를 조정해도 증상이 그대로다. 브라우저 콘솔과 네트워크 탭을 먼저 본다.

## 4. DB 동시 연결 수 (커넥션 풀)

"어떤 때는 되고 어떤 때는 안 된다"의 전형적인 원인이다. Supabase의 Postgres는 연결을 중개하는 층(pgBouncer, transaction 모드)을 통해 붙고, 그 층에 전체 연결 수 상한이 있다.

**먼저 재현한다.** 실패하는 화면이 실행하는 것과 같은 쿼리를 임시 스크립트로 만들어 연달아 여러 번 실행한다.

```bash
npx tsx -r dotenv/config scripts/_check.mjs dotenv_config_path=.env.local
```

한 번 `statement timeout`으로 실패하고 나머지가 빠르게 성공하는 식의 기록이 나오면 그것이 근거다. 확인이 끝나면 임시 스크립트를 지운다.

**고치는 위치**는 DB 클라이언트를 만드는 파일이다(보통 `src/db/index.ts`). 서버 함수는 인스턴스마다 자기 연결 묶음을 따로 만들기 때문에, 서버 하나를 기준으로 잡은 `max` 값이 동시에 뜬 인스턴스 수만큼 곱해져서 상한을 넘는다. 조정할 것 세 가지:

- **`max`를 서버리스일 때만 낮춘다.** `process.env.VERCEL`을 기준으로 나눈다. 전역으로 낮추면 로컬 개발서버나 데이터 넣는 스크립트가 같이 느려진다.
- **`idle_timeout`을 넣는다.** 일이 끝난 인스턴스가 자기 연결을 계속 붙잡고 있지 않고 놓게 한다.
- **`connect_timeout`을 넣는다.** 연결이 부족할 때 끝나지 않는 요청이 아니라 몇 초 안에 읽을 수 있는 에러로 끝나게 한다. 근본 원인을 다 잡기 전이라도 이건 넣는 게 낫다.

## 5. DB가 잠들어 있는 경우

Supabase 무료 플랜은 일정 기간 사용이 없으면 프로젝트를 자동으로 멈춘다(Pro 플랜은 해당 없음). 처음 한 번만 아주 느리거나 실패하고 그다음부터 잘 되면 이쪽이다.

플랜이 뭔지 모르면 사용자에게 한 줄로 물어본다. 연결 수 조정에 시간을 쓰기 전에 확인한다.
