지금 변경(working tree, 지정한 commit, PR)을 읽고 무슨 일이 생겼는지 설명한다. 서론 없이 시작한다.

먼저 `git status`와 `git diff`(필요하면 `git diff --staged`, `git diff <base>`)로 실제 변경을 읽는다. 읽지 않은 것은 말하지 않는다.

출력 순서:

1. **한 줄 요약** — 사용자에게 무엇이 달라지는가. 예: "회원 목록에 메모 칸이 생긴다."
2. **바뀐 곳** — 파일 이름 대신 역할로 말한다. "화면(…tsx)", "DB 설계도인 드리즐 스키마(schema.ts)", "변경 지시서인 마이그레이션 파일(drizzle/*.sql)", "환경 변수(.env.example)". 파일마다 한 줄.
3. **무엇이 어떻게** — diff 블록으로 보여준다. 함수 전체가 아니라 바뀐 줄 앞뒤만 남기고, 블록 위에 한 문장으로 뜻을 적는다.

```diff
 participants 표
   id
   name
+  note        // 비워둘 수 있는 메모 칸
```

4. **영향** — 해당하는 것만. 드리즐 스키마(DB 구조)가 바뀜(migration 필요) / 환경 변수 이름이 추가됨 / 화면이 바뀜 / 기존 데이터를 지우거나 바꿈 / 없음.
5. **확인할 것** — 사람이 직접 확인할 화면이나 동작 하나. diff에 있지만 이유를 모르는 변경은 "이유 확인이 어려움"으로 남긴다.

규칙:
- 은유를 쓰지 않는다. "무엇이 어디에 생겼다 / 없어졌다 / 바뀌었다"로 말한다.
- 용어는 처음 한 번만 짧게 풀어 쓴다. 예: migration(DB 구조를 바꾸는 지시서).
- 코드 줄이 아니라 결과로 설명한다. "if를 추가했다"가 아니라 "이름이 비어 있으면 저장하지 않는다."
- 잘했다, 나쁘다 평가는 하지 않는다. 물어보면 답한다.
- 짧게. 변경이 크면 사용자에게 달라지는 것 기준으로 3개까지만 다루고 나머지는 한 줄 목록으로 남긴다.
